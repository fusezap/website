Engineering notes

Last updated 19 October 2026. Written for compiler, runtime and ML-systems engineers.

This page says exactly what FuseZap is, what we have measured, and what isn’t done yet. If something here doesn’t match what you see when we work together, tell us.

What FuseZap is

FuseZap is a compiler and serving engine for LLM inference. A model is expressed in about 28 primitive operations. The compiler schedules and fuses them into kernels, generates source for the target, and tunes launch parameters with a beam search. The serving layer runs on top of whatever the compiler produces.

Porting to a new chip means writing one backend. A backend has four parts:

  • Renderer: turns our kernel IR into source in your kernel language (a C dialect, or an LLVM or MLIR-level entry point).
  • Compiler hook: calls your toolchain to build that source into something your chip runs. Builds are cached on disk.
  • Runtime: loads kernels and launches them through your driver API.
  • Allocator: device memory through your driver.

The backend only needs a way to compile a kernel and a way to launch it, so a functional simulator with the same interface works before silicon exists. On a simulator we prove correctness; performance tuning waits for real hardware.

Tuned kernels you already have, such as matmul or attention, plug in through a custom-kernel hook and are called directly instead of generated. Everything above the backend is shared by every chip: the compiler passes, the model code, the serving engine and the tests.

Why not a vLLM plugin?

It’s a fair question, and for some teams a plugin is the right answer. vLLM describes itself as running any model on any hardware, and its hardware support is real, but in practice each chip it supports builds on its maker’s own PyTorch or JAX backend and hand-tuned kernels. vLLM’s hardware plugin interface gives you its scheduler, batching and API. What it doesn’t give you is the kernels. Your team still writes and tunes kernels for the operations each model uses, and every time a model introduces a new attention variant, activation or quantization format, that work starts again. You also follow vLLM’s internals, which change often.

FuseZap works one level lower. Models are built from about 28 primitive operations, and the compiler fuses and generates kernels for your chip from those, tuning them with a beam search. A new model is mostly a new combination of the same primitives, so it should need little or no new kernel work. Your tuned matmul and attention kernels still plug in where they’re faster.

That is a claim we intend to prove, not just make. On our first non-GPU accelerator (AWS Inferentia2, in progress) we’re recording how much backend code, time and money the first model takes, and then the second. We’ll publish both numbers here.

Hardware capability contract (v0)

This is what a chip needs to offer for a FuseZap backend. It is a first version; the Inferentia2 port is testing it now, and we’ll version it as it changes.

Multiple devicesNot yetTensor and pipeline parallelism across chips are not part of v0. They’re planned once a design partner needs models larger than one chip can hold.

Real chips don’t always fit a clean interface. Inferentia2 already breaks a few of these assumptions: shapes are fixed when a kernel is compiled, its kernel language works on whole tiles rather than threads, and its compiler has to run in a separate process. We’ll publish every exception we hit, along with how we handled it.

Correctness method

  • Operations: every primitive and composed op is tested against NumPy and PyTorch on four execution tiers (a pure-Python interpreter, NumPy, compiled CPU and Metal).
  • Training parity: a small GPT trains with losses matching PyTorch within 1e-4 on every tier.
  • Models: Qwen2.5-0.5B-Instruct produces 64 greedy tokens identical to Hugging Face Transformers at FP32. Chat templates match Hugging Face for six tokenizers (Qwen2.5, Llama 3.0 to 3.2, Mistral and SmolLM2).
  • 7B on NVIDIA: Qwen2.5-7B-Instruct in bf16 on an H100 picks the same next token as the Hugging Face FP32 reference at 99.3% of 1,024 positions (our bar is 99%, and Hugging Face’s own bf16 scores 99.1%).
  • Batching: 32 concurrent requests each produce tokens bit-identical to running alone, including under chunked prefill and preemption.
  • API: the server is exercised with OpenAI’s official Python client, including streaming and concurrent streams.

FuseZap vs vLLM on an NVIDIA H100 (October 2026)

Qwen2.5-7B-Instruct, FuseZap and vLLM 0.32.0 run back to back on the same H100 80GB machine. Each request has 512 tokens in and 128 out, greedy decoding, three repetitions after a warm-up, unique prompts so no cache helps either engine. vLLM runs at its defaults. What isn’t done yet

  • No custom accelerator backend yet. Today: CPU, Apple Metal and NVIDIA CUDA. AWS Inferentia2 is next, and AMD HIP follows.
  • Still slower than vLLM: 70% of its throughput for one user and 53% at 32 users on the same H100. Generating tokens for many users at once is the main gap.
  • Tested up to 7B on a single GPU. Mixture-of-experts and multi-device sharding are not tested yet.
  • No prefix caching. Tool calls are rendered into the prompt but not parsed, and logprobs are not returned.
  • FP8 runs natively on NVIDIA H100 (weights and activations); on other backends it is weight-only.
